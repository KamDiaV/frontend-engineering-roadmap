# VIII. Accessibility и ARIA

### 1. Что такое accessibility (a11y)?

**Accessibility**, или **веб-доступность**, — это подход к разработке сайтов и приложений, при котором интерфейсом могут пользоваться люди с различными возможностями и способами взаимодействия с компьютером.

Часто используется сокращение:

```text
a11y
```

Оно образовано от слова:

```text
accessibility
```

между первой буквой `a` и последней `y` находится 11 букв.

Accessibility касается не только пользователей скринридеров.

Она включает поддержку людей:

- с нарушениями зрения;
- с нарушениями слуха;
- с двигательными ограничениями;
- с когнитивными особенностями;
- временно ограниченных в возможностях;
- использующих клавиатуру вместо мыши;
- использующих вспомогательные технологии.

Например, доступный интерфейс должен позволять выполнить основные действия только с клавиатуры:

```text
Tab
Enter
Space
Escape
Arrow keys
```

Доступность обеспечивается несколькими уровнями:

```text
семантический HTML
        ↓
правильная структура документа
        ↓
keyboard accessibility
        ↓
доступные имена и описания
        ↓
ARIA при необходимости
        ↓
визуальная доступность
```

К accessibility относятся, например:

- логичная структура заголовков;
- `<label>` для элементов формы;
- альтернативный текст изображений;
- достаточный цветовой контраст;
- видимый `focus`;
- возможность управления с клавиатуры;
- использование нативных HTML-элементов;
- корректное применение ARIA.

---

### 2. Что такое ARIA?

**ARIA — Accessible Rich Internet Applications** — набор атрибутов, позволяющих передавать вспомогательным технологиям дополнительную информацию о роли, состоянии и свойствах элементов интерфейса.

Например:

```html
<button aria-expanded="false">
  Меню
</button>
```

`aria-expanded` сообщает, раскрыт или закрыт связанный интерфейс.

ARIA включает несколько типов информации.

#### Roles

Определяют роль элемента:

```html
<div role="button">
  Отправить
</div>
```

#### States

Описывают состояние:

```html
<button aria-expanded="true">
  Меню
</button>
```

#### Properties

Передают дополнительные свойства:

```html
<input aria-describedby="password-help">
```

Главный принцип:

> ARIA изменяет информацию, доступную accessibility API, но сама по себе обычно не добавляет поведение элементу.

Например:

```html
<div role="button">
  Сохранить
</div>
```

получает семантику кнопки для вспомогательных технологий, но автоматически не получает всё клавиатурное поведение настоящего `<button>`.

#### Короче:

ARIA — набор атрибутов, который позволяет описывать роли, состояния и свойства элементов для вспомогательных технологий.

ARIA следует использовать для дополнения HTML-семантики, когда нативного HTML недостаточно.

---

### 3. Что такое `role`?

Атрибут `role` определяет **семантическую роль элемента для accessibility API**.

Например:

```html
<div role="button">
  Открыть меню
</div>
```

Здесь вспомогательные технологии могут воспринимать `<div>` как кнопку.

Другие примеры ролей:

```html
role="dialog"
role="alert"
role="navigation"
role="tab"
role="tabpanel"
```

Роль сообщает:

> чем является этот элемент в интерфейсе.

Однако `role` не изменяет нативное поведение HTML-элемента.

Например:

```html
<div role="button">
```

не начинает автоматически:

- реагировать на `Space`;
- реагировать на `Enter`;
- получать фокус;
- вести себя полностью как `<button>`.

Поэтому, если существует подходящий нативный HTML-элемент, обычно следует использовать его.

Например, вместо:

```html
<div role="button">
  Сохранить
</div>
```

лучше:

```html
<button type="button">
  Сохранить
</button>
```

Кроме явно указанных ARIA roles, многие HTML-элементы уже имеют **implicit role**.

Например:

```html
<button>
```

уже имеет роль `button`.

---

### 4. Для чего используется `aria-label`?

`aria-label` задаёт элементу **доступное имя — accessible name** в виде строки.

Например, кнопка только с иконкой:

```html
<button
  type="button"
  aria-label="Закрыть"
>
  ×
</button>
```

Визуально пользователь видит:

```text
×
```

а вспомогательная технология получает имя:

```text
Закрыть
```

`aria-label` полезен, когда у интерактивного элемента нет подходящего видимого текста, который мог бы использоваться как его доступное имя.

Например:

```html
<button aria-label="Поиск">
  <svg aria-hidden="true">
    ...
  </svg>
</button>
```

Не следует без необходимости добавлять `aria-label` элементам, у которых уже есть понятное доступное имя.

Например:

```html
<button>
  Отправить
</button>
```

уже имеет доступное имя `Отправить`.

Добавлять:

```html
<button aria-label="Отправить">
  Отправить
</button>
```

обычно не требуется.

---

### 5. Чем `aria-label` отличается от обычного `<label>`?

`<label>` — нативный HTML-элемент для создания подписи элемента формы.

Например:

```html
<label for="email">
  Email
</label>

<input
  id="email"
  type="email"
  name="email"
>
```

Он создаёт программную связь между текстом и элементом управления.

Кроме того, пользователь может нажать на `<label>`, чтобы взаимодействовать со связанным полем.

`aria-label`:

```html
<input
  type="email"
  aria-label="Email"
>
```

задаёт доступное имя для вспомогательных технологий, но **не создаёт видимую подпись**.

То есть:

```text
<label>
→ видимая подпись
→ программная связь
→ увеличивает область взаимодействия

aria-label
→ доступное имя
→ обычно не виден пользователю
```

Для обычных полей формы предпочтительно использовать `<label>`.

`aria-label` используется, когда подходящей видимой подписи действительно нет.

#### Короче:

`<label>` создаёт видимую и программно связанную подпись для элемента формы.

`aria-label` задаёт только доступное имя для вспомогательных технологий и не заменяет видимую подпись там, где она нужна.

---

### 6. Что такое `aria-labelledby`?

`aria-labelledby` позволяет задать доступное имя элемента **с помощью текста другого элемента или нескольких элементов**.

Например:

```html
<h2 id="dialog-title">
  Удалить файл?
</h2>

<div
  role="dialog"
  aria-labelledby="dialog-title"
>
  ...
</div>
```

Значение:

```html
aria-labelledby="dialog-title"
```

ссылается на:

```html
id="dialog-title"
```

В результате доступным именем диалога становится:

```text
Удалить файл?
```

Можно ссылаться на несколько элементов:

```html
<span id="first-name">Диана</span>
<span id="action">профиль</span>

<div aria-labelledby="first-name action">
  ...
</div>
```

`aria-labelledby` особенно полезен, когда нужный текст уже видим на странице.

В таком случае не требуется дублировать его:

```html
aria-label="..."
```

#### Короче:

`aria-labelledby` задаёт доступное имя элемента через содержимое другого элемента.

Для этого указывается `id` элемента, содержащего текст:

```html
aria-labelledby="title"
```

---

### 7. Что такое `aria-describedby`?

`aria-describedby` связывает элемент с текстом, который предоставляет **дополнительное описание**.

Например:

```html
<label for="password">
  Пароль
</label>

<input
  id="password"
  type="password"
  aria-describedby="password-help"
>

<p id="password-help">
  Пароль должен содержать не менее 8 символов.
</p>
```

Здесь:

```text
label
→ что это за поле

aria-describedby
→ дополнительная информация о поле
```

Доступное имя отвечает на вопрос:

```text
Что это?
```

Описание отвечает:

```text
Что ещё нужно знать об этом элементе?
```

`aria-describedby` часто используется для:

- подсказок;
- инструкций;
- сообщений об ограничениях;
- дополнительного поясняющего текста.

---

### 8. Когда следует использовать ARIA?

ARIA следует использовать, когда **семантики нативного HTML недостаточно для корректного описания интерфейса**.

Основной принцип:

```text
сначала нативный HTML
        ↓
ARIA только при необходимости
```

Например, обычная кнопка:

```html
<button type="button">
  Сохранить
</button>
```

не требует:

```html
role="button"
```

потому что семантика уже встроена.

ARIA особенно полезна для сложных динамических компонентов, например:

- tabs;
- dialogs;
- combobox;
- tree;
- custom widgets;
- раскрывающиеся элементы;
- сообщения состояния.

Например:

```html
<button
  type="button"
  aria-expanded="false"
  aria-controls="menu"
>
  Меню
</button>
```

Здесь HTML предоставляет кнопку, а ARIA добавляет информацию о состоянии связанного компонента.

---

### 9. Почему правило «No ARIA is better than bad ARIA» важно?

Неправильно применённая ARIA может сделать интерфейс **менее доступным**, чем если бы ARIA вообще не использовалась.

Например, разработчик может написать:

```html
<div role="button">
  Отправить
</div>
```

и считать, что получил полноценную кнопку.

Однако роль не добавляет:

- клавиатурное управление;
- фокусируемость;
- стандартное браузерное поведение.

Другой пример — неправильная роль:

```html
<button role="heading">
  Отправить
</button>
```

Так можно разрушить корректную встроенную семантику `<button>`.

ARIA влияет на то, как элемент представлен в accessibility tree, поэтому ошибка может передать вспомогательной технологии ложную информацию.

Главный принцип:

```text
правильный HTML
лучше
неправильного ARIA
```

---

### 10. Почему лучше использовать нативный `<button>`, чем `<div role="button">`?

Нативный `<button>` уже предоставляет семантику и поведение кнопки:

```html
<button type="button">
  Сохранить
</button>
```

Он:

- распознаётся как кнопка;
- включён в последовательность фокуса;
- работает с клавиатурой;
- реагирует на `Enter`;
- реагирует на `Space`;
- имеет ожидаемое браузерное поведение;
- доступен вспомогательным технологиям.

Если использовать:

```html
<div role="button">
  Сохранить
</div>
```

роль добавит только часть семантики.

Разработчику придётся самостоятельно реализовать, например:

```html
tabindex="0"
```

и клавиатурное поведение через JavaScript.

Например:

```js
element.addEventListener('keydown', (event) => {
  if (event.key === 'Enter' || event.key === ' ') {
    // выполнить действие
  }
});
```

Кроме того, нужно корректно обрабатывать множество деталей поведения.

Поэтому действует принцип:

> Используйте нативный HTML, когда подходящий элемент существует.

### 11. Что такое accessibility tree?

**Accessibility tree** — специальное представление интерфейса, которое браузер формирует для accessibility APIs и вспомогательных технологий.

Упрощённо:

```text
HTML / DOM
    ↓
семантика элементов
ARIA
CSS-состояние
    ↓
Accessibility Tree
    ↓
Accessibility API
    ↓
Screen Reader
```

Accessibility tree не является точной копией DOM.

Он содержит информацию, важную для взаимодействия:

- роль элемента;
- доступное имя;
- описание;
- состояние;
- значение;
- отношения между элементами.

Например:

```html
<button>
  Сохранить
</button>
```

может быть представлен концептуально как:

```text
Role: button
Name: "Сохранить"
```

А:

```html
<input
  type="checkbox"
  checked
  aria-label="Получать уведомления"
>
```

как:

```text
Role: checkbox
Name: "Получать уведомления"
State: checked
```

Некоторые элементы DOM могут вообще не присутствовать в accessibility tree, если они не несут информации для вспомогательных технологий.

---

### 12. Что такое focusable element?

**Focusable element** — элемент, который способен получить keyboard focus.

Когда элемент находится в фокусе, клавиатурные действия пользователя направляются на него.

Например:

```html
<button type="button">
  Отправить
</button>
```

Кнопка может получить фокус.

Многие интерактивные HTML-элементы фокусируемы по умолчанию:

```html
<a href="/about">О нас</a>

<button>Сохранить</button>

<input>

<select></select>

<textarea></textarea>
```

Переход между фокусируемыми элементами обычно выполняется клавишей:

```text
Tab
```

а в обратную сторону:

```text
Shift + Tab
```

Важно различать:

```text
focusable
```

и:

```text
входит в последовательность Tab
```

Элемент может быть программно фокусируемым, но не находиться в обычной Tab-последовательности, например при:

```html
tabindex="-1"
```

---

### 13. Что такое `tabindex`?

`tabindex` — глобальный HTML-атрибут, управляющий возможностью элемента получать фокус и его участием в последовательной keyboard navigation.

Например:

```html
<div tabindex="0">
  ...
</div>
```

Основные варианты:

```text
tabindex="0"
tabindex="-1"
tabindex="1" и выше
```

`tabindex` влияет прежде всего на **sequential focus navigation**, то есть перемещение между элементами клавишей `Tab`.

Нативным интерактивным элементам обычно не требуется задавать `tabindex`:

```html
<button>
  Отправить
</button>
```

уже доступен через `Tab`.

`tabindex` следует использовать осознанно, потому что изменение порядка фокуса может существенно повлиять на keyboard accessibility.

---

### 14. Чем отличаются `tabindex="0"` и `tabindex="-1"`?

### `tabindex="0"`

```html
<div tabindex="0">
  ...
</div>
```

делает элемент:

- фокусируемым;
- включённым в обычную Tab-последовательность.

Его положение в последовательности определяется порядком элементов в документе.

Упрощённо:

```text
DOM order
↓
Tab order
```

### `tabindex="-1"`

```html
<div tabindex="-1">
  ...
</div>
```

делает элемент программно фокусируемым, но исключает его из обычной последовательной навигации через `Tab`.

Например:

```js
element.focus();
```

может установить на него фокус.

Это полезно, например, когда после открытия интерфейса нужно программно переместить фокус на определённый элемент.

Главное различие:

```text
tabindex="0"
→ можно попасть через Tab

tabindex="-1"
→ через Tab обычно нельзя,
  но можно установить фокус программно
```

#### Короче:

`tabindex="0"` делает элемент частью обычной Tab-навигации.

`tabindex="-1"` исключает его из Tab-последовательности, но позволяет установить фокус программно.

---

### 15. Почему обычно не рекомендуется использовать положительный `tabindex`?

Положительные значения:

```html
tabindex="1"
tabindex="2"
tabindex="3"
```

создают специальный порядок последовательной навигации.

Например:

```html
<button tabindex="3">A</button>
<button tabindex="1">B</button>
<button tabindex="2">C</button>
```

Tab-порядок может отличаться от визуального и DOM-порядка.

Это создаёт проблемы:

- порядок фокуса становится сложнее понимать;
- DOM и keyboard navigation расходятся;
- при добавлении новых элементов приходится управлять номерами;
- интерфейс становится сложнее поддерживать;
- пользователю сложнее предсказывать перемещение фокуса.

Обычно предпочтительнее позволять браузеру использовать естественный DOM-порядок:

```html
<button>A</button>
<button>B</button>
<button>C</button>
```

При необходимости элемент можно добавить в естественную последовательность через:

```html
tabindex="0"
```

---

### 16. Что такое keyboard accessibility?

**Keyboard accessibility** означает, что пользователь может пользоваться интерфейсом с клавиатуры без необходимости использовать мышь или touch-интерфейс.

Все основные интерактивные действия должны быть доступны с клавиатуры.

Основные клавиши:

```text
Tab
Shift + Tab
Enter
Space
Escape
Arrow keys
```

Например:

```text
Tab
→ переход между элементами

Enter
→ активация ссылки или кнопки

Space
→ активация некоторых controls

Escape
→ закрытие некоторых интерфейсов

Arrow keys
→ навигация внутри определённых widgets
```

Важная часть keyboard accessibility — **видимый focus indicator**.

Например:

```css
button:focus-visible {
  outline: 2px solid currentColor;
  outline-offset: 3px;
}
```

Пользователь должен понимать, какой элемент сейчас находится в фокусе.

Хорошая keyboard accessibility обычно достигается проще при использовании нативных HTML-элементов.

#### Короче:

Keyboard accessibility — возможность полностью использовать основные функции интерфейса с помощью клавиатуры.

Она требует логичного порядка фокуса, правильного клавиатурного поведения и видимого состояния фокуса.

---

### 17. Что такое landmark regions?

**Landmark regions** — крупные смысловые области страницы, которые помогают вспомогательным технологиям определять структуру интерфейса.

Примеры landmarks:

```text
banner
navigation
main
complementary
contentinfo
search
form
region
```

Пользователь скринридера может перемещаться между такими областями, не проходя последовательно через каждый элемент страницы.

Например, страница:

```html
<header>
  ...
</header>

<nav>
  ...
</nav>

<main>
  ...
</main>

<aside>
  ...
</aside>

<footer>
  ...
</footer>
```

может предоставлять несколько landmarks:

```text
banner
navigation
main
complementary
contentinfo
```

Landmarks создают своего рода крупную карту страницы.

Если на странице несколько landmarks одного типа, им часто требуется доступное имя, чтобы их можно было различить.

Например:

```html
<nav aria-label="Основная навигация">
  ...
</nav>

<nav aria-label="Навигация по статье">
  ...
</nav>
```

#### Короче:

Landmark regions — крупные семантические области страницы, которые помогают пользователям вспомогательных технологий быстро перемещаться между основными частями интерфейса.

---

### 18. Какие HTML-элементы создают landmarks автоматически?

Некоторые семантические HTML-элементы имеют **implicit ARIA roles** и при соответствующем контексте создают landmarks автоматически.

### `<main>`

```html
<main>
  ...
</main>
```

создаёт landmark:

```text
main
```

---

### `<nav>`

```html
<nav>
  ...
</nav>
```

создаёт:

```text
navigation
```

---

### `<aside>`

```html
<aside>
  ...
</aside>
```

обычно создаёт:

```text
complementary
```

---

### `<header>`

В определённом контексте `<header>` может создавать:

```text
banner
```

Например, когда он представляет header всего документа:

```html
<body>
  <header>
    ...
  </header>
</body>
```

Но `<header>` внутри `<article>` не становится автоматически общим `banner` страницы.

---

### `<footer>`

Аналогично `<footer>` страницы может иметь роль:

```text
contentinfo
```

Но footer внутри отдельного `<article>` не является общим `contentinfo` документа.

---

### `<form>`

`<form>` может создавать landmark `form`, когда имеет доступное имя, например:

```html
<form aria-labelledby="search-title">
  <h2 id="search-title">Поиск по каталогу</h2>
  ...
</form>
```

---

### `<section>`

`<section>` может соответствовать landmark `region`, если имеет доступное имя.

Например:

```html
<section aria-labelledby="news-title">
  <h2 id="news-title">
    Новости
  </h2>

  ...
</section>
```

---

### `<search>`

Современный HTML также содержит элемент:

```html
<search>
  ...
</search>
```

который представляет область поиска и соответствует landmark `search`.

---

Основная идея:

```text
семантический HTML
        ↓
implicit ARIA semantics
        ↓
landmarks в accessibility tree
```

Поэтому обычно не нужно писать:

```html
<nav role="navigation">
```

Достаточно:

```html
<nav>
```

поскольку соответствующая семантика уже встроена.

#### Короче:

Landmarks автоматически могут создавать, в зависимости от контекста:

```text
<main>    → main
<nav>     → navigation
<aside>   → complementary
<header>  → banner
<footer>  → contentinfo
<form>    → form при наличии accessible name
<section> → region при наличии accessible name
<search>  → search
```

Поэтому семантический HTML обычно предпочтительнее явного добавления ARIA roles.

### 19. Что такое ARIA states и properties и чем они отличаются от roles?

ARIA описывает интерфейс с помощью:

```text
roles
states
properties
```

### Roles

**Role** отвечает на вопрос:

> Что это за элемент?

Например:

```html
<div role="checkbox">
  ...
</div>
```

Здесь элемент представлен вспомогательным технологиям как checkbox.

### States

**States** описывают текущее состояние элемента, которое может изменяться во время взаимодействия.

Например:

```html
<button aria-expanded="false">
  Меню
</button>
```

После открытия меню:

```html
<button aria-expanded="true">
  Меню
</button>
```

То есть:

```text
role
→ что это?

state
→ в каком состоянии это находится сейчас?
```

Примеры states:

```text
aria-expanded
aria-checked
aria-selected
aria-pressed
```

### Properties

**Properties** передают дополнительные характеристики или отношения элемента.

Например:

```html
<input
  aria-describedby="password-help"
>
```

`aria-describedby` связывает поле с дополнительным описанием.

Другие примеры:

```text
aria-label
aria-labelledby
aria-describedby
aria-controls
```

Граница между states и properties в повседневной разработке не всегда принципиальна, и их часто вместе называют **ARIA states and properties**. WAI-ARIA использует их для передачи accessibility API дополнительной информации о виджетах и интерфейсе.

#### Короче

```text
role
→ что это за элемент

state
→ его текущее изменяемое состояние

property
→ дополнительная характеристика или связь
```

---

### 20. Для чего используются `aria-expanded`, `aria-controls`, `aria-selected` и `aria-checked`?

Эти ARIA-атрибуты описывают состояние и отношения интерактивных элементов.

### `aria-expanded`

Показывает, раскрыт или свернут связанный интерфейс.

```html
<button
  aria-expanded="false"
  aria-controls="menu"
>
  Меню
</button>
```

После открытия:

```html
<button
  aria-expanded="true"
  aria-controls="menu"
>
  Меню
</button>
```

Типичные случаи:

- dropdown;
- accordion;
- disclosure;
- expandable menu.

---

### `aria-controls`

Указывает, каким элементом управляет текущий элемент.

Значением является `id` связанного элемента:

```html
<button
  aria-expanded="false"
  aria-controls="menu"
>
  Меню
</button>

<div id="menu">
  ...
</div>
```

Связь:

```text
aria-controls="menu"
         ↓
id="menu"
```

`aria-controls` описывает отношение между элементами, но само по себе не реализует управление.

---

### `aria-selected`

Показывает, выбран ли элемент внутри интерфейса, где существует понятие selection.

Например, tab:

```html
<button
  role="tab"
  aria-selected="true"
>
  Описание
</button>
```

Другой tab:

```html
<button
  role="tab"
  aria-selected="false"
>
  Характеристики
</button>
```

Используется, например, для:

- tabs;
- listbox options;
- grid items в подходящих паттернах.

---

### `aria-checked`

Показывает checked-состояние элемента, который имеет соответствующую ARIA role.

Например:

```html
<div
  role="checkbox"
  aria-checked="false"
>
  Получать новости
</div>
```

После выбора:

```html
<div
  role="checkbox"
  aria-checked="true"
>
  Получать новости
</div>
```

Некоторые роли поддерживают также:

```text
aria-checked="mixed"
```

для промежуточного состояния.

Если существует нативный HTML-контрол:

```html
<input type="checkbox">
```

предпочтительнее использовать его, а не создавать собственный checkbox через ARIA.

#### Короче

```text
aria-expanded
→ раскрыт / свернут

aria-controls
→ каким элементом управляет

aria-selected
→ выбран ли элемент

aria-checked
→ отмечен ли checkbox-подобный элемент
```

### 21. Что такое live regions и для чего используется `aria-live`?

**Live region** — область страницы, содержимое которой может динамически изменяться, и об этих изменениях нужно сообщить пользователю вспомогательной технологии без переноса фокуса в эту область.

Например, после добавления товара в корзину:

```html
<div
  aria-live="polite"
  id="status"
></div>
```

JavaScript:

```js
status.textContent =
  'Товар добавлен в корзину';
```

Фокус пользователя остаётся на кнопке, но screen reader может сообщить новое сообщение.

`aria-live` определяет приоритет уведомления.

Основные значения:

```text
off
polite
assertive
```

### `aria-live="polite"`

```html
<div aria-live="polite">
  ...
</div>
```

Сообщение обычно озвучивается тогда, когда это не мешает текущей речи screen reader.

Подходит для большинства обычных обновлений:

- товар добавлен;
- данные загрузились;
- результат поиска обновился.

### `aria-live="assertive"`

```html
<div aria-live="assertive">
  ...
</div>
```

Сообщение имеет высокий приоритет и может прервать текущее объявление.

Использовать его следует только для действительно важной информации.

### `aria-live="off"`

Изменения не должны объявляться как live updates в обычном режиме.

Live regions нужны именно для **динамических изменений, происходящих без перемещения фокуса**.

#### Короче

Live region — динамически обновляемая область, изменения которой могут автоматически сообщаться screen reader.

`aria-live` задаёт приоритет таких сообщений:

```text
polite
assertive
off
```
